
# Customer Module Specification

## 1. Overview

The Customer module is responsible for creating, storing, retrieving, and searching corporate customers.

Each customer represents a company that uses SaaS-O-Matic to generate subscription simulations.

The module must ensure that customer information is valid and that duplicate tax identification numbers are not registered within the same country.

## 2. Customer Data Model

Each customer must contain the following information:

| Field | Type | Required | Description |
|---|---|---|---|
| id | Integer | Generated | Unique customer identifier |
| company_name | String | Yes | Company name |
| tax_id | String | Yes | Tax identification number |
| email | String | Yes | Contact email |
| country | String | Yes | Country code (ISO 3166-1 alpha-2) |
| plan | String | Yes | Selected subscription plan |
| created_at | Datetime | Generated | Customer creation timestamp |

### 2.1. Field Constraints

- `company_name` must not be empty or contain only whitespace.
- `tax_id` must not be empty.
- `email` must have a valid email format.
- `country` must contain a valid ISO 3166-1 alpha-2 country code.
- `plan` must correspond to a supported subscription plan.
- `id` and `created_at` are generated by the backend.

## 3. API Endpoints

### 3.1. Create Customer

**Endpoint:** `POST /customers`

Creates a new customer.

**Request body:**

```json
{
  "company_name": "Example Corporation",
  "tax_id": "B12345678",
  "email": "contact@example.com",
  "country": "ES",
  "plan": "basic"
}
```

**Processing steps:**

1. Validate the request structure and required fields.
2. Normalize the tax identification number according to the defined rules.
3. Validate the tax identification number according to the customer's country.
4. Check whether the tax identification number already exists for that country.
5. Create and persist the customer.
6. Return the created customer.

**Successful response:** `201 Created`

```json
{
  "id": 1,
  "company_name": "Example Corporation",
  "tax_id": "B12345678",
  "email": "contact@example.com",
  "country": "ES",
  "plan": "basic",
  "created_at": "2026-01-15T10:30:00Z"
}
```

**Possible errors:**

| HTTP Status | Error | Description |
|---|---|---|
| 422 | Validation Error | Invalid or missing request fields |
| 409 | Duplicate Customer | Tax ID already registered in that country |
| 500 | Internal Server Error | Unexpected server error |

### 3.2. List and Search Customers

**Endpoint:** `GET /customers`

Retrieves customers and optionally filters them by company name or tax identification number.

**Query parameters:**

| Parameter | Type | Required | Description |
|---|---|---|---|
| search | String | No | Search term matching company name or tax ID |

**Example:**

`GET /customers?search=Example`

**Successful response:** `200 OK`

```json
[
  {
    "id": 1,
    "company_name": "Example Corporation",
    "tax_id": "B12345678",
    "email": "contact@example.com",
    "country": "ES",
    "plan": "basic",
    "created_at": "2026-01-15T10:30:00Z"
  }
]
```

An empty array must be returned when no customers match the search criteria.

### 3.3. Retrieve Customer Details

**Endpoint:** `GET /customers/{customer_id}`

Retrieves the information of a specific customer.

**Successful response:** `200 OK`

Returns the customer object.

**Possible errors:**

| HTTP Status | Error | Description |
|---|---|---|
| 404 | Customer Not Found | No customer exists with the specified ID |

## 4. Tax Identification Validation

Tax identification numbers must be validated according to the customer's country.

For the initial implementation:

- Spanish DNI/NIF validation must follow the official control-character algorithm.
- Spanish CIF validation must follow the applicable official format and control-character rules.
- Other countries may initially use basic format validation where a specific validation algorithm has not been implemented.

The validation logic must be isolated in a dedicated service so that additional countries and identification formats can be supported later.

Invalid tax identification numbers must be rejected before customer creation.

## 5. Business Rules

- **CUS-BR-01:** Every customer must have a unique internal ID.
- **CUS-BR-02:** Company name, tax ID, email, country, and plan are mandatory.
- **CUS-BR-03:** Tax identification numbers must be validated according to the customer's country.
- **CUS-BR-04:** A tax ID cannot be registered more than once within the same country.
- **CUS-BR-05:** Customers can be searched by company name or tax ID.
- **CUS-BR-06:** Customer records must be persisted in SQLite.
- **CUS-BR-07:** Customer deletion is restricted when associated simulations exist.

## 6. Validation and Error Handling

The API must return clear and consistent validation errors.

- Missing required fields must be rejected.
- Invalid email addresses must be rejected.
- Invalid country codes must be rejected.
- Unsupported subscription plans must be rejected.
- Invalid tax identification numbers must be rejected.
- Duplicate tax IDs must return HTTP 409.
- Requests for non-existent customers must return HTTP 404.

## 7. Acceptance Criteria

The Customer module will be considered complete when:

- [ ] A customer can be created using valid information.
- [ ] Required fields are validated.
- [ ] Email addresses are validated.
- [ ] Country codes are validated.
- [ ] Spanish DNI/NIF and CIF identifiers are validated correctly.
- [ ] Duplicate tax IDs within the same country are rejected.
- [ ] Customers can be searched by company name.
- [ ] Customers can be searched by tax ID.
- [ ] Customer details can be retrieved by ID.
- [ ] Customer information is persisted in SQLite.
- [ ] Appropriate HTTP status codes and error messages are returned.
